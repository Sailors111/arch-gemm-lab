# 基于体系结构技术的 GEMM 性能优化实验设计

> 课程：2026 秋《高级计算机体系结构》
> 实验工程：`gemm-lab/`
> 文档性质：实验设计方案；测量结果、分析与结论见 [report.md](report.md)

---

## 1. 实验目标

本实验以方阵乘法 C = A×B（M=N=K=n，FP32，行优先）为载体，回答两个问题：

1. **单一体系结构技术的优化效果**：循环重排、缓存分块、数据打包、SIMD 寄存器分块、多线程分别能带来多少加速比？矩阵规模如何影响这些收益？
2. **多技术组合的极限与因素**：把上述技术逐层叠加后，最佳配置是什么？缓存容量、内存带宽、TLB、指令级并行、线程数、频率等因素分别如何影响最终性能？

实验以朴素 i-j-k 实现为基线（T0），T1–T6 每引入一种技术，保持输入、编译选项、测量协议完全一致，只改变被考察的变量。

## 3. 统一实验框架

### 3.1 统一接口

`gemm-lab/src/gemm.h` 定义所有变体共用的签名：

```c
typedef struct {
    int mb, nb, kb;   /* 分块大小 */
    int nthreads;     /* OpenMP 线程数 */
} gemm_params;

typedef void (*gemm_fn)(const float *A, const float *B, float *C,
                        int M, int N, int K, const gemm_params *p);
```

`bench` 在运行时通过函数指针选择变体，保证所有实现走同一条测量路径。

### 3.2 beta = 0 语义

所有变体约定：本次计算覆盖 C，不读取旧值。

- T0、T1 直接写 C；
- T2–T6 和 best 内部使用 `C += ...`，因此调用方必须在每次调用前清零 C。

清零由 `bench` 负责，且**放在计时区之外**：

```c
memset(C, 0, cn * sizeof(float));   /* 不计时 */
double t0 = now_sec();
v->fn(A, B, C, n, n, n, &p);
double dt = now_sec() - t0;
```

### 3.3 测量协议

1. 矩阵用 `posix_memalign(64)` 分配，不计分配和初始化时间；
2. 输入用固定种子的伪随机数生成，取值 `[-1,1)`，保证可复现；
3. 用双精度 i-k-j 实现生成参考解，只算一次；
4. 热身默认 2 次，不计时；
5. 计时用 `clock_gettime(CLOCK_MONOTONIC)`，只包住一次 GEMM 调用；
6. 重复次数自适应：
   - 首次计时后补足到约 1 秒；
   - 最少 3 次；单次已 ≥2 秒时最少 2 次；
   - 上限 30 次；
7. 报告**中位数**，同时记录 min/max 观察稳定性；
8. 第一次重复后与参考解比对，不通过则不作为性能结果。

### 3.4 正确性指标

对每个元素计算：

$$
\text{abs-err}_{ij} = |C_{ij} - C^{\text{ref}}_{ij}|,\qquad
\text{rel-err}_{ij} = \frac{|C_{ij} - C^{\text{ref}}_{ij}|}{\max(1, |C^{\text{ref}}_{ij}|)}
$$

报告两者的最大值。

阈值采用长度为 K 的 FP32 累加一阶误差界：

$$
\text{rel-err} \le K \cdot \varepsilon_{\text{float}},\qquad
\varepsilon_{\text{float}} = \texttt{FLT-EPSILON} \approx 1.19\times10^{-7}
$$

对应规模：

| K | 128    | 256    | 512    | 1024   | 2048   | 3072   | 4096   |
| ----- | ------ | ------ | ------ | ------ | ------ | ------ | ------ |
| 阈值  | 1.5e-5 | 3.1e-5 | 6.1e-5 | 1.2e-4 | 2.4e-4 | 3.7e-4 | 4.9e-4 |

本机 T0 基线实测误差为 0.20–0.30 Kε，留 3–5 倍余量。使用 FMA 或双精度累加时误差通常更小，该上界仍然适用。

### 3.5 性能指标

| 指标               | 定义                                                             | 用途               |
| ------------------ | ---------------------------------------------------------------- | ------------------ |
| `time_s`         | 一次 GEMM 调用的墙钟时间                                         | 基础测量           |
| GFLOPS             | 2n³/t×10⁹                                  | 有效吞吐           |
| 加速比（对基线）   | `S_v(n) = t_naive(n)/t_v(n)`                 | 单一技术收益       |
| 加速比（对上一层） | `S_(v\|u) = t_u(n)/t_v(n)`                         | 逐层叠加的边际收益 |
| 并行效率           | `E_p = S_p/p`                                         | T6 的强扩展性      |
| 有效算术强度       | AI = 2n³/实际搬运字节数              | Roofline 分析      |
| 打包开销比         | `(t_pack - t_block)/t_block` | T4 的额外成本      |
| 误差               | 见 3.4                                                           | 正确性门槛         |

可选的硬件计数：`cache-misses`、`dTLB-load-misses`、`cycles`、`instructions`。本机 `perf` 部分可用，`LLC-loads/LLC-misses` 不支持；若无法获取，用 Roofline 和规模趋势间接分析。

## 4. 变体设计

### T0：朴素 i-j-k 基线

**原理**

最直白的定义式实现：

```c
for (int i = 0; i < M; ++i)
    for (int j = 0; j < N; ++j) {
        float acc = 0.0f;
        for (int k = 0; k < K; ++k)
            acc += A[i * K + k] * B[k * N + j];
        C[i * N + j] = acc;
    }
```

行优先存储下：

- `A[i*K + k]` 随 k 连续，访问友好；
- `B[k*N + j]` 随 k 每次跳 N 个 float，是跨步访问；
- 对固定 j，每读一个 B 元素只用到 64 B 缓存行中的 4 B，缓存行利用率 1/16。

**复杂度与访存**

- 浮点运算：2n³；
- B 的元素被读取 n 次，且每次跨步，理论上产生 n³ 次缓存行访问；
- 有效算术强度（按缓存行计）约 2/64 = 0.031 FLOP/B；
- 内层 `acc` 是串行依赖，编译器在不开 `-ffast-math` 时难以向量化。

**预期现象**

- 小规模工作集能进 L2/L3，性能尚可；
- 规模超过 L3 后 GFLOPS 明显下降；
- 大规模下受访存延迟和 TLB 限制，而不是浮点算力限制。

**本机基线实测（已采集）**

|    n | 中位时间 | GFLOPS |
| ---: | -------: | -----: |
|  128 |  1.42 ms |   2.95 |
|  256 | 17.93 ms |   1.87 |
|  512 | 128.2 ms |   2.09 |
| 1024 |  2.090 s |   1.03 |
| 2048 |  57.20 s |   0.30 |
| 3072 |  206.3 s |   0.28 |
| 4096 |  571.5 s |   0.24 |

### T1：i-k-j 循环重排

**原理**

把 k 循环提到 j 外面，最内层对 j 连续更新 C 的一行：

```c
for (int i = 0; i < M; ++i) {
    const float *ai = A + (size_t)i * K;
    float *ci = C + (size_t)i * N;
    for (int k = 0; k < K; ++k) {
        const float a = ai[k];
        const float *bk = B + (size_t)k * N;
        for (int j = 0; j < N; ++j)
            ci[j] += a * bk[j];
    }
}
```

对每个 C 元素，k 的累加顺序与 T0 相同，所以数值结果基本一致；改变的是**访存顺序**：B 的行和 C 的行都变成连续访问，缓存行利用率从 1/16 提升到接近 1。

**代价**

- C 的一行会被写 K 次；但该行只有 4N 字节，n=4096 时为 16 KiB，可以留在 L1/L2；
- A 的每个元素只读一次，B 的每一行被读 M 次（每个 i 一次），总读取量仍是 n³ 量级，但都是顺序访问。

**预期**

- 大规模下明显优于 T0，因为消除了跨步访问和缓存行浪费；
- 小规模下提升有限，因为 T0 本来就能放进缓存；
- 仍然没有分块，B 的完整行在多个 i 之间无法保证驻留，规模大时仍受容量限制。

**观察指标**

- GFLOPS–n 曲线的拐点是否右移；
- 相同 n 下 `dTLB-load-misses` 是否下降（若 perf 可用）。

---

### T2/T3：缓存分块

**原理**

把 M、N、K 三个方向切成 `mb × nb × kb` 的小块，块内仍用 i-k-j：

```c
for (i0 = 0; i0 < M; i0 += mb)
  for (j0 = 0; j0 < N; j0 += nb)
    for (k0 = 0; k0 < K; k0 += kb)
      for (i = i0; i < i1; ++i)
        for (k = k0; k < k1; ++k) {
            float a = A[i*K + k];
            for (j = j0; j < j1; ++j)
                C[i*N + j] += a * B[k*N + j];
        }
```

三个块的作用：

- C 的 `mb × nb` 块在 k 方向被反复使用，目标驻留 L2；
- B 的 `kb × nb` 块被 `mb` 行复用；
- A 的 `mb × kb` 块被 `nb` 列复用。

**T2 与 T3 的区分**

- T2（单级分块）：只在一个方向分块，例如固定 `kb = K`，只切 i/j；
- T3（多级分块）：i/j/k 三个方向都切，形成两级或三级块，分别匹配 L1、L2、L3。

代码中由同一函数 `gemm_block` 实现三级分块。做 T2 实验时，可通过参数退化为单级，例如 `--kb 4096`（等价于不切 k）或 `--mb 4096`（不切 i）。

**块大小选择**

设每个 float 4 B：

- L1 约 48 KiB：`(mb + nb) * kb * 4` 不宜超过 L1；
- L2 约 1.25 MiB：`mb * nb * 4` 应能放下 C 块；
- 默认 `64/64/64` 时，A/B 块各 16 KiB，C 块 16 KiB，能进 L1/L2。

**预期**

- 规模超过 L2/L3 后收益最大；
- 块太小 → 循环开销和边界处理占比上升；
- 块太大 → 工作集溢出，退化为 T1；
- 存在一个随 n 变化的最优块大小，这正是“矩阵大小影响”的一部分。

**观察指标**

- 不同 `mb/nb/kb` 下的 GFLOPS 热力图；
- 与 T1 对比，拐点是否继续右移；
- 小规模下是否因分块开销出现负收益。

### T4：数据打包

**原理**

分块解决了“块能否放下”，但块内 B 的行起点仍可能不对齐、跨页或与 C 争用缓存组。打包把块复制到连续、对齐的临时缓冲区：

- B 面板：`Bp[k * nb_act + j]`，大小 `K × nb`；
- A 面板：`Ap[i * K + k]`，大小 `mb × K`。

核心代码：

```c
/* 打包 B 面板 */
for (int k = 0; k < K; ++k) {
    const float *src = B + (size_t)k * N + j0;
    float *dst = Bp + (size_t)k * nb_act;
    for (int j = 0; j < nb_act; ++j)
        dst[j] = src[j];
}

/* 打包 A 面板 */
for (int i = 0; i < mb_act; ++i)
    memcpy(Ap + (size_t)i * K,
           A + (size_t)(i0 + i) * K,
           (size_t)K * sizeof(float));

/* 在打包面板上计算 */
for (int k = k0; k < k0 + kb_act; ++k) {
    float a = ai[k];
    const float *bk = Bp + (size_t)k * nb_act;
    for (int j = 0; j < nb_act; ++j)
        ci[j] += a * bk[j];
}
```

**代价与收益**

- 打包是额外的内存搬运，量级约为计算量的 1/nb；
- 收益是块内访问完全连续、对齐，便于编译器向量化，也为 T5 的微内核准备规整布局；
- 打包缓冲区按线程私有，避免竞争。

**预期**

- 单独使用时，T4 相对 T3 的提升可能不大，甚至在小规模下因打包开销略慢；
- 主要价值是**为 T5 创造条件**：微内核需要连续、可预测的 B 行和 A 列；
- 观察打包开销随 nb 的变化：nb 越大，打包相对开销越小。

**观察指标**

- T4 与 T3 的差值（打包净收益）；
- 小规模是否出现负收益；
- 不同 nb 下 GFLOPS 与打包时间估算。

### T5：寄存器分块 + AVX2/FMA 微内核

**原理**

在打包/分块的基础上，对 C 的 `8 × 8` 块使用 8 个 `__m256` 累加器常驻寄存器：

- 每次 k，B 的一行 8 个 float 用一次 256 位 load；
- A 的 8 个元素分别广播；
- 做 8 次 FMA；
- K 循环结束后一次性写回 C。

核心代码：

```c
__m256 c0 = _mm256_loadu_ps(C + (i0 + 0) * N + j0);
/* ... c1 ... c7 ... */

for (int k = 0; k < K; ++k) {
    __m256 bv = _mm256_loadu_ps(B + k * N + j0);
    c0 = _mm256_fmadd_ps(_mm256_set1_ps(A[(i0 + 0) * K + k]), bv, c0);
    /* ... c1 ... c7 ... */
}

_mm256_storeu_ps(C + (i0 + 0) * N + j0, c0);
/* ... 其余 7 行 ... */
```

**体系结构意义**

- 每个 B 元素被 8 行复用，每个 A 元素服务 8 列；
- 每次 FMA 处理 8 个 float，理论峰值从标量的每周期 2 FLOP 提升到每周期数十 FLOP；
- 8 个累加器提供指令级并行，掩盖 FMA 的 4–5 周期延迟；
- 边界（M/N 不是 8 的倍数）用标量补全，保证通用性。

**预期**

- 相对 T1/T3 有数量级提升，尤其在中等规模、数据能进 L2 时；
- 大规模下仍受 B 的访存限制，需要 T4 的打包和 T2 的分块配合；
- 若无 AVX2/FMA，代码自动退回标量 i-k-j。

**观察指标**

- GFLOPS 是否接近 Roofline 的算力上界；
- 与 T4 的差值（寄存器分块本身的收益）；
- 边界规模（如 n=129、n=1000）是否出现明显掉点。

### T6：OpenMP 多线程

**原理**

按 C 的行划分任务，每个线程负责若干完整行：

```c
#pragma omp parallel for schedule(static) num_threads(nt)
for (int i = 0; i < M; ++i) {
    const float *ai = A + (size_t)i * K;
    float *ci = C + (size_t)i * N;
    for (int k = 0; k < K; ++k) {
        float a = ai[k];
        const float *bk = B + (size_t)k * N;
        for (int j = 0; j < N; ++j)
            ci[j] += a * bk[j];
    }
}
```

**设计要点**

- 行与行之间没有数据依赖，不需要同步或归约；
- 每行长度 4N 字节，n≥128 时至少 512 B，行边界不会造成明显的伪共享；
- `schedule(static)` 适合每行工作量相同的 GEMM；
- 线程数由 `gemm_params.nthreads` 控制，便于做强扩展实验。

**预期**

- 计算受限时接近线性加速；
- 访存受限时（T0/T1 大规模）加速比明显低于线程数，因为多个线程共享 L3 和内存带宽；
- 4 核 8 线程的机器上，4 线程通常效率最高，8 线程可能因超线程争用而收益递减。

**观察指标**

- 强扩展：固定 n，线程数 1/2/4/8 的时间与并行效率；
- 弱扩展（可选）：总工作量随线程数增长时的时间；
- 与单线程 T5 对比，判断瓶颈是算力还是带宽。

---

### 组合最优：best

**设计**

把 T2/T3、T4、T5、T6 叠加：

1. OpenMP 按 `j0` 列块并行，各线程写不同的 C 列块；
2. 每个线程私有 `Bp`、`Ap` 打包缓冲区；
3. B 的 `K × nb` 面板打包一次；
4. 对每个 `i0`，打包 A 的 `mb × K` 面板；
5. 在 `kb` 子块上运行 8×8 AVX2 微内核。

**消融实验**

从 best 出发，逐项关闭一个技术，观察性能回落：

| 配置           | 变化                                  |
| -------------- | ------------------------------------- |
| best           | 全开                                  |
| best − OpenMP | `--threads 1`                       |
| best − SIMD   | 编译时禁用 AVX2，或替换为标量打包版本 |
| best − 打包   | 退回 T2/T3                            |
| best − 分块   | 退回 T1/T5                            |

通过消融可以回答“哪个因素贡献最大”，而不是只给一个最终数字。

**参数**

- `mb/nb/kb`：默认 64/64/64，扫描 32/64/128/256；
- `threads`：1/2/4/8；
- `n`：128–4096。

**预期**

- 大规模下 best 应显著优于任一单项技术；
- 小规模下可能不如纯 T5，因为打包和并行启动开销占比高；
- 最佳配置可能随 n 变化，形成“分段最优”的结论。

## 5. 实验矩阵与执行计划

### 5.1 第一阶段：单一技术

固定单线程（T6 除外），对 T0–T6 扫描：

```text
n ∈ {128, 256, 512, 1024, 2048, 3072, 4096}
```

得到“技术 × 规模”的加速比表和 GFLOPS 曲线。

### 5.2 第二阶段：矩阵大小的影响

对每个技术画 GFLOPS–n 和 speedup–n，重点观察：

- 工作集 3n²×4 B 跨越 L2（1.25 MiB）、L3（8 MiB）时的拐点；
- 分块、打包、SIMD 分别把拐点右移多少；
- 大规模下是否进入带宽/延迟平台。

### 5.3 第三阶段：组合与消融

- 累加栈：T0 → T1 → T2/T3 → T4 → T5 → T6 → best；
- 消融：从 best 逐项移除；
- 记录每一层的边际加速比，而不只是总加速比。

### 5.4 第四阶段：参数扫描

- 块大小：`mb/nb/kb ∈ {32, 64, 128, 256}`；
- 线程数：`1/2/4/8`；
- 对每个 n 找最优配置，形成“最佳配置 = f(n, 线程预算)”。

## 6. 数据分析方法

### 6.1 Roofline

理论模型：

$$
P \le \min\left(P_{\text{peak}},\ \text{AI} \times B_{\text{mem}}\right)
$$

- 理想 GEMM 的算术强度 AI = n/6 FLOP/B；
- T0 由于 B 的跨步访问，按缓存行计算的有效 AI ≈ 2/64 = 0.031 FLOP/B；
- 把实测 GFLOPS 与 `P_peak`、`AI×B_mem` 比较，判断每个变体是算力受限还是带宽受限。

### 6.2 缓存层次分析

工作集：

$$
W(n) = 3n^2 \times 4\ \text{B}
$$

|    n |  工作集 | 预期行为                  |
| ---: | ------: | ------------------------- |
|  128 | 192 KiB | 进 L2，性能高             |
|  512 |   3 MiB | 进 L3，仍较好             |
| 1024 |  12 MiB | 超过 L3，开始明显下降     |
| 2048 |  48 MiB | 主要访存，分块收益最大    |
| 4096 | 192 MiB | 带宽/延迟受限，TLB 压力大 |

### 6.3 TLB 与访存模式

- T0 的 B 访问步长为 4N B：n=4096 时 16 KiB，跨多个 4 KiB 页；
- 统计 `dTLB-load-misses`（若 perf 可用）；
- T1/T2/T4 应显著降低 TLB miss，T5 的连续 B 行访问进一步降低。

### 6.4 并行效率

$$
E_p = \frac{S_p}{p} = \frac{t_1}{p \cdot t_p}
$$

- `E_p` 接近 1：计算受限，扩展性好；
- `E_p` 随 p 下降：带宽或共享缓存成为瓶颈；
- 结合 4 核 8 线程的超线程特性分析。

### 6.5 统计与误差

- 每个配置至少 3 次（自适应可更多），报告中位数；
- 同时给出 min/max，若 max/min 超过 10%，说明测量噪声大，应增加重复次数；
- 小规模（n≤256）单次只有毫秒级，必须用自适应重复或手动 `--reps 20`。

## 7. 预期结论（假设，待实验验证）

1. **T1** 在大规模下明显优于 T0，但小规模提升有限；拐点右移。
2. **T2/T3** 在 n≥1024 时收益最大，能把 GFLOPS 下降的拐点推迟；块大小存在最优值。
3. **T4** 单独收益有限，但为 T5 提供连续布局，是组合方案的必要环节。
4. **T5** 带来数量级提升，使中等规模进入算力受限区；大规模仍需分块和打包配合。
5. **T6** 在计算受限时接近线性加速，在带宽受限时加速比明显低于线程数。
6. **best** 在大规模下取得最高加速比；小规模可能不如纯 T5，体现“没有万能的配置”。
7. 最终最佳配置随 n 和线程数变化，可用分段函数描述。

以上均为待验证假设，实验报告将以实测数据为准，不预先填入结论。

## 8. 风险与对策

| 风险                    | 影响             | 对策                                                                   |
| ----------------------- | ---------------- | ---------------------------------------------------------------------- |
| WSL 读不到真实频率/温度 | 无法直接解释降频 | 在 Windows 侧用 HWiNFO 记录；固定电源计划                              |
| `perf` 部分事件不可用 | 缺少 LLC 计数    | 用 `cache-misses`、`dTLB-load-misses` 和 Roofline 间接分析         |
| 大规模 naive 运行时间长 | 数据采集慢       | 自适应重复（≥2 s 时只跑 2 次）、`--warmup 1`、必要时 `--no-check` |
| 小规模计时噪声大        | 中位数不稳       | 自适应重复或 `--reps 20`                                             |
| 误差阈值不合理          | 误判正确性       | 使用 Kε 公式，并记录实测比值                             |
| 分块/打包边界错误       | 结果不正确       | n=65、n=129 等非 2 幂规模做边界测试                                    |
| 多线程伪共享            | 扩展性下降       | 按行/列块划分，保证块边界对齐缓存行                                    |
| 内存不足                | 打包缓冲区过大   | 限制块大小；best 每线程缓冲区约 `(K*nb + mb*K)*4` B                  |
